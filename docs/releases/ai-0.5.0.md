# ai-dotnet release 0.5.0

**Qwen3.5 int4 and guided decoding on the hosted files, GLiNER2 text classification, reranking helpers, and generated capability records for every model package.** This release follows the `0.4.0` record (`ai-0.4.0.md`, merged in #272; see Publishing) and carries the work merged since: round 2 of the backlog sweep (#259, #260, #261, #264, #265, #267, #268, #269, #270, #271, integrated by #273; #262 and #263 are design notes only) and round 3 (#274, #275). The publishable set is unchanged at **27 packages**: no package joins or leaves it. `Starlings.Models.Qwen3Embedding` and `Starlings.Models.Qwen3Embedding.Extensions.AI` are new in the repository but **source only, pending the reranker decision** (#144, #100; see [Not published](#packages)). The one compile break is `KevModelProfile`'s two new `required` members (#246); the lock of every Qwen3.5 variant gains two files (hosting revision r2), so a cache acquired earlier must download again. See [Upgrading](#upgrading-from-040).

**Publishing.** The `release` workflow publishes this release from the tag `ai-v0.5.0` on `main`, after a maintainer approves the `release` environment. It publishes the 27 packages of the publishable set below through NuGet trusted publishing, and creates a GitHub release with this record as notes. When this candidate was prepared, `ai-v0.4.0` had not been pushed and nuget.org's last ai-dotnet version was `0.3.0` (2026-10-19). `0.4.0` can still be tagged on the commit its record describes, `d9b003f` (the merge of #272); then this record is the step from `0.4.0`. If `0.4.0` is never tagged, `0.5.0` is the first published version after `0.3.0`, and the [upgrade notes](#upgrading-from-040) of both records apply.

**Tokenizer.** Unchanged: every package that tokenizes pins `Starlings.Tokenizers [0.3.4]`, as in `0.4.0`. `0.3.5` follows in a later release.

**Maturity.** Maturity belongs to profiles, not packages, and each package README has a generated maturity table. Every Stable profile of `0.4.0` is still Stable with the same contract: no gate, tolerance or `protected/` file changed. On the Stable Qwen3.5 profiles (`ortgenai-fp32x-cpu`, `ortgenai-fp32x-cuda`, `ortgenai-fp16x-cuda`), `structured_output` moves from unsupported to experimental (guided decoding on the hosted r2 files); the Stable contracts are unchanged. The E5 CUDA manifest now states `concurrent_calls` (Supported), which its README contract already said. New registry profiles:

## Changes merged since 0.4.0

Everything below was merged to `main` after the `0.4.0` record (moved here from `docs/releases/unreleased.md`).

### Starlings.Models.Abstractions: reranking helpers for vector-search pipelines (Experimental; #168)

New `Reranking` and `RerankedItem<T>(Item, Index, Score)` put an `IReranker` (today `BertReranker`, for example `bge-reranker-v2-m3`) after a first-stage retriever. Microsoft.Extensions.AI has no reranker abstraction, so the helpers take any sequence plus a text selector and add no package reference: `RerankAsync` reads an `IAsyncEnumerable<T>` such as a `Microsoft.Extensions.VectorData` `SearchAsync` top-k, scores it with one `Score` call and orders by descending score (ties in input order, optional `top`); `Rerank` is the synchronous form; `AsScoringFunction` wraps an `IReranker` as a `Func<string, IReadOnlyList<string>, Task<float[]>>`, and a `RerankAsync` overload takes any such scorer. `AsScoringFunction` scores synchronously and returns a completed task; `RerankAsync` validates its arguments synchronously and scores after the last candidate arrives, on the thread that resumed it. API only and Experimental; every reranker profile stays Experimental (the Stable `bge-reranker-v2-m3` profile is still open in #168).

### Starlings.Models.E5: `concurrent_calls` recorded for the CUDA profile; README qualification runner (#258, #252)

- `E5Capabilities.ProfileCapabilities["multilingual-e5-small/onnx-fp32-cuda"].Capabilities` (and the obsolete `E5Capabilities.Profiles`) now contains `concurrent_calls`, `Supported`, generated from the registry manifest, which now states it explicitly. The status is not new: the README's "Stable contract: CUDA" and `E5Capabilities.Statuses["concurrent_calls"]` already said supported, and code that read a missing key as anything else now sees it. Evidence for Supported: the binding RTX 3090 G4 one-hour soak of this profile, which ran with 2 concurrent callers (`docs/evidence/qualification-2026-10-16-cuda/`). Extra local coverage: `docs/evidence/cuda-concurrency-2026-11-01/` (RTX 4060 Ti, a local check, not qualification; #257 tracks the RTX 3090 rerun of that check).
- The "Supported platform" rows of the E5, EmbeddingGemma 2, GLiNER2 and Qwen3.5 (ONNX Runtime GenAI) READMEs keep the GitHub-hosted `ubuntu-latest` record of the weekly qualification up to 2026-10-22 and add the self-hosted `qualification` runner it runs on since #134 (Intel Core i7-5820K, AVX2, no AVX-512, transparent huge pages `madvise`). No contract changes.

### EmbeddingGemma 2 image and video CUDA: concurrent-call tests (#257)

New CUDA tests run overlapping `EmbedBatch` calls on one `EmbeddingGemma2MultimodalEmbedder` for `image-fp32-cuda` (4 threads by default, `STARLING_EG2_CUDA_IMAGE_CONCURRENT_THREADS` to change it) and `video-fp32-cuda` (8 threads), and compare every vector with the sequential result byte for byte. Both passed on an RTX 4060 Ti (experimental evidence; the RTX 3090 rerun is open in #257). `concurrent_calls` stays supported. The package README now warns that 8 overlapping image calls on one embedder ran out of device memory on a 16 GB GPU (`OnnxRuntimeException`, not a wrong result) until memory-aware limits land (#172). Evidence: `docs/evidence/cuda-concurrency-2026-11-01/`.

### Generated capability records for every model package (#177)

`ModelProfileCapabilities` records, generated from the registry manifests by `model-pipeline catalog` (`ProfileCapabilities.g.cs`, checked by `catalog --check`), now cover every registered profile, not only e5, EmbeddingGemma 2 and GLiNER2. New members: `BertCapabilities.ProfileCapabilities` (the seven BERT-family profiles), `KevCapabilities.ProfileCapabilities` (`Starlings.Models.Kev.Onnx`), `Qwen35Capabilities.ProfileCapabilities` (`Starlings.Models.Qwen35.OnnxGenAI`), the new `QwenChatCapabilities.ProfileCapabilities` (`Starlings.Models.QwenChat.OnnxGenAI`), `Lfm3Capabilities.ProfileCapabilities` and `WhisperCapabilities.ProfileCapabilities`. Each package's contract tests compare every record with its manifest field for field. **Dependency change:** `Starlings.Models.Kev.Onnx`, `Starlings.Models.Qwen35.OnnxGenAI`, `Starlings.Models.QwenChat.OnnxGenAI`, `Starlings.Models.Lfm3` and `Starlings.Models.Whisper` now depend on `Starlings.Models.Abstractions` (which references only `Starlings.Acquisition`). The existing package-wide tables (`All`, `Profiles`) are unchanged. The generation-specific fields of #177 (tool-call mode, structured output, state/prefix reuse, caching style and max output tokens) are not in the record yet.

### Starlings.Models.Gliner2: text classification, Experimental on CPU (#183, step 1)

The new `Gliner2TextClassifier` runs GLiNER2's classification head over an extractor's session. It takes a task name and at least two labels, and returns a logit and a score per label and GLiNER2's answer (single-label: softmax argmax; multi-label: sigmoid against a threshold, with the best label as fallback). It reads the locked graph's `last_hidden_state` at the `[L]` markers, so no new graph is needed. The head comes from the checkpoint's `model.safetensors`: `Gliner2ClassificationHead.FromSafetensors` reads only the 4.7 MB head and checks it against `HeadSha256`. `Gliner2ModelAssets.ClassificationLock` adds that file (834 MB, from the Hub repository at the pinned commit) to the entity lock.

The capability `classification` is now `experimental` on `gliner2-base-v1/onnx-fp32-cpu`. On 26 proposed cases run by the pinned GLiNER2, input ids and decisions were exact, logits were within 2.74e-5 relative and scores within 8.46e-6 (`docs/evidence/gliner2-classification-2026-11-01/`). It stays `unsupported` on CUDA: the classifier rejects CUDA sessions. Several tasks per call, label descriptions, temperature and batching are `unsupported`. There is no task-quality set yet, and parity is not quality: at least 2 of the 19 single-label answers in those cases are wrong for GLiNER2 itself. Entity extraction is unchanged: the protected entity parity passes, with exact inputs.

### Starlings.Models.EmbeddingGemma2: opt-in vision batch limits from free memory (experimental, #172)

New `EmbeddingGemma2MultimodalOptions.AutoBatchLimits` (`EmbeddingGemma2AutoBatchLimits`, default `null`: off). When set, `EmbeddingGemma2MultimodalEmbedder` reads the free memory of the vision graph's device once after load (Linux host `MemAvailable`, capped by the least room under a cgroup v2 `memory.max` of the process's cgroup or its ancestors, on CPU; `cuMemGetInfo` of the CUDA driver, capped at `gpu_mem_limit` when set, on CUDA) and raises `MaxVisionBatchSize`, `MaxVideoFramesPerVisionCall` and `MaxVisionBatchPatches` to what fits in `(free - ReservedBytes) * UsableFraction` (defaults 1 GiB and 0.5), with an estimate of 3 GiB per full-budget image derived from the CUDA observations behind the defaults. Configured values are floors; `MaxImagesPerCall` (8) and `MaxFramesPerCall` (16) cap the raise; the text-graph limits are not changed. With the option set, vision-graph calls run one at a time; batched CUDA outputs match single calls within about 3.4e-5, not bit for bit. `EmbeddingGemma2MultimodalEmbedder.AutoBatchAvailableBytes` reports the bytes read (`null` when the probe is unavailable, and then the configured limits apply). Capability `image.auto_batch_limits`: Experimental (the estimate is not measured per device; no qualification run). The defaults are unchanged, so no Stable contract moves. The CUDA probe was checked on an RTX 4060 Ti (opt-in CUDA test), which supports Experimental only.

### Starlings.Models.Qwen3Embedding and .Extensions.AI: source only, not published in this release (Experimental; #144, #108, #100)

### Starlings.Models.Qwen35.OnnxGenAI: int4 on CPU (Experimental; #163)

New `Qwen35Variant.Int4` and registry profile `qwen3.5-0.8b/ortgenai-int4-cpu` (Experimental). The graph is the ONNX Runtime GenAI 0.17.1 builder's int4 CPU recipe (`-p int4 -e cpu`: round-to-nearest, block 32, accuracy level 4) on the float32-overlay snapshot, built with `model-pipeline/reference/generation/build_ortgenai_bundle.py --variant int4`. ### Starlings.Models.Kev: KevState on CUDA (#140)

`state_reuse_across_calls.cuda` moves from untested to **experimental**. The KevState tests now also run in the local CUDA test project (`CudaParityTests.StateReuseEqualsDecideBitForBit`, `StateIsSharedByConcurrentCallsAndRefusedAfterDispose`). On `kev-0.8b/onnx-fp32-cuda`, decisions from a `KevState` equal `Decide(request)` on the same CUDA session bit for bit: the nine request goldens, twice in a row and question by question, and from four concurrent callers. This passed in 3 of 3 processes on an RTX 4060 Ti, not the RTX 3090. Kev-4B on CUDA was not run, since it needs about 17 GB of device memory. No code change. Evidence: `docs/evidence/kev-state-cuda-2026-11-01/`. The GPU-resident `-e cuda` graph (#140 ask 1) and cross-request prefix reuse are still open.

## Upgrading from 0.4.0

If you are upgrading from `0.3.0` (because `0.4.0` was not published), first apply every item of [Upgrading from 0.3.0](ai-0.4.0.md#upgrading-from-030) in `ai-0.4.0.md`, which includes the breaking generation package split; then the items below.

- Raise every `Starlings.*` reference to `0.5.0` together. The tokenizer stays at `0.3.4`.
- Stable profiles produce the same outputs; no default changed.
- **`KevModelProfile` (breaking at compile time).** Code that creates its own `KevModelProfile` with an object initializer must set the new `required` members `CheckpointLock` and `BaseCheckpointLock` (error CS9035 otherwise). `KevModelProfile.Kev08B`, `Kev4B`, `All` and `with` copies are unaffected. This is an exception to the one-minor-version notice ([support policy](../support-policy.md#public-api-deprecation), rule 5): a new `required` member cannot first be announced with `[Obsolete]`, and the members are `required` so that no `KevModelProfile` exists without the checkpoint locks that pin its Hub files. See [`BREAKING.md`](BREAKING.md#050).
- **Qwen3.5 caches.** Each variant's lock (`Qwen35ModelAssets.GetLock`) now includes `ortgenai-<variant>/tokenizer.json` and `tokenizer_config.json`: `Qwen35ModelAssets.OpenLocal` and `OpenDirectory` throw `ModelAssetMissingException` on a cache acquired earlier until `DownloadAsync` runs again (about 20 MB for fp32x or fp16x), whether or not guidance is used. A directory built with an earlier bundle script needs the same two files.
- `Qwen35ModelAssets.DownloadAsync(Qwen35Variant.Int4)` downloads instead of throwing `NotSupportedException` (first download about 0.58 GB).
- `Starlings.Models.Kev` and `Starlings.Models.QwenChat` now bring `Starlings.Acquisition`; `Starlings.Models.Kev.Onnx`, `Starlings.Models.Qwen35.OnnxGenAI`, `Starlings.Models.QwenChat.OnnxGenAI` and `Starlings.Models.Lfm3` now bring `Starlings.Models.Abstractions`. Both come in transitively at the same version.
- `E5Capabilities.ProfileCapabilities["multilingual-e5-small/onnx-fp32-cuda"].Capabilities` now contains `concurrent_calls` (Supported); code that read the missing key as anything else sees the stated status.
- Nothing is removed. The members marked `[Obsolete]` in `0.4.0` are still present and behave as before (see [`BREAKING.md`](BREAKING.md#pending-removals)).
