# ai-dotnet: unreleased changes

Changes merged to `main` after the last release record, collected here for the next one. The release-candidate change moves them into `ai-<version>.md` and empties this file. Nothing here is published until then.

## Starlings.Models.Abstractions: reranking helpers for vector-search pipelines (Experimental; #168)

New `Reranking` and `RerankedItem<T>(Item, Index, Score)` put an `IReranker` (today `BertReranker`, for example `bge-reranker-v2-m3`) after a first-stage retriever. Microsoft.Extensions.AI has no reranker abstraction, so the helpers take any sequence plus a text selector and add no package reference: `RerankAsync` reads an `IAsyncEnumerable<T>` such as a `Microsoft.Extensions.VectorData` `SearchAsync` top-k, scores it with one `Score` call and orders by descending score (ties in input order, optional `top`); `Rerank` is the synchronous form; `AsScoringFunction` wraps an `IReranker` as a `Func<string, IReadOnlyList<string>, Task<float[]>>`, and a `RerankAsync` overload takes any such scorer. `AsScoringFunction` scores synchronously and returns a completed task; `RerankAsync` validates its arguments synchronously and scores after the last candidate arrives, on the thread that resumed it. API only and Experimental; every reranker profile stays Experimental (the Stable `bge-reranker-v2-m3` profile is still open in #168).

## Starlings.Models.E5: `concurrent_calls` recorded for the CUDA profile; README qualification runner (#258, #252)

- `E5Capabilities.ProfileCapabilities["multilingual-e5-small/onnx-fp32-cuda"].Capabilities` (and the obsolete `E5Capabilities.Profiles`) now contains `concurrent_calls`, `Supported`, generated from the registry manifest, which now states it explicitly. The status is not new: the README's "Stable contract: CUDA" and `E5Capabilities.Statuses["concurrent_calls"]` already said supported, and code that read a missing key as anything else now sees it. Evidence for Supported: the binding RTX 3090 G4 one-hour soak of this profile, which ran with 2 concurrent callers (`docs/evidence/qualification-2026-10-16-cuda/`). Extra local coverage: `docs/evidence/cuda-concurrency-2026-11-01/` (RTX 4060 Ti, a local check, not qualification; #257 tracks the RTX 3090 rerun of that check).
- The "Supported platform" rows of the E5, EmbeddingGemma 2, GLiNER2 and Qwen3.5 (ONNX Runtime GenAI) READMEs keep the GitHub-hosted `ubuntu-latest` record of the weekly qualification up to 2026-10-22 and add the self-hosted `qualification` runner it runs on since #134 (Intel Core i7-5820K, AVX2, no AVX-512, transparent huge pages `madvise`). No contract changes.

## EmbeddingGemma 2 image and video CUDA: concurrent-call tests (#257)

New CUDA tests run overlapping `EmbedBatch` calls on one `EmbeddingGemma2MultimodalEmbedder` for `image-fp32-cuda` (4 threads by default, `STARLING_EG2_CUDA_IMAGE_CONCURRENT_THREADS` to change it) and `video-fp32-cuda` (8 threads), and compare every vector with the sequential result byte for byte. Both passed on an RTX 4060 Ti (experimental evidence; the RTX 3090 rerun is open in #257). `concurrent_calls` stays supported. The package README now warns that 8 overlapping image calls on one embedder ran out of device memory on a 16 GB GPU (`OnnxRuntimeException`, not a wrong result) until memory-aware limits land (#172). Evidence: `docs/evidence/cuda-concurrency-2026-11-01/`.

## Generated capability records for every model package (#177)

`ModelProfileCapabilities` records, generated from the registry manifests by `model-pipeline catalog` (`ProfileCapabilities.g.cs`, checked by `catalog --check`), now cover every registered profile, not only e5, EmbeddingGemma 2 and GLiNER2. New members: `BertCapabilities.ProfileCapabilities` (the seven BERT-family profiles), `KevCapabilities.ProfileCapabilities` (`Starlings.Models.Kev.Onnx`), `Qwen35Capabilities.ProfileCapabilities` (`Starlings.Models.Qwen35.OnnxGenAI`), the new `QwenChatCapabilities.ProfileCapabilities` (`Starlings.Models.QwenChat.OnnxGenAI`), `Lfm3Capabilities.ProfileCapabilities` and `WhisperCapabilities.ProfileCapabilities`. Each package's contract tests compare every record with its manifest field for field. **Dependency change:** `Starlings.Models.Kev.Onnx`, `Starlings.Models.Qwen35.OnnxGenAI`, `Starlings.Models.QwenChat.OnnxGenAI`, `Starlings.Models.Lfm3` and `Starlings.Models.Whisper` now depend on `Starlings.Models.Abstractions` (which references only `Starlings.Acquisition`). The existing package-wide tables (`All`, `Profiles`) are unchanged. The generation-specific fields of #177 (tool-call mode, structured output, state/prefix reuse, caching style and max output tokens) are not in the record yet.

## Starlings.Models.Gliner2: text classification, Experimental on CPU (#183, step 1)

The new `Gliner2TextClassifier` runs GLiNER2's classification head over an extractor's session. It takes a task name and at least two labels, and returns a logit and a score per label and GLiNER2's answer (single-label: softmax argmax; multi-label: sigmoid against a threshold, with the best label as fallback). It reads the locked graph's `last_hidden_state` at the `[L]` markers, so no new graph is needed. The head comes from the checkpoint's `model.safetensors`: `Gliner2ClassificationHead.FromSafetensors` reads only the 4.7 MB head and checks it against `HeadSha256`. `Gliner2ModelAssets.ClassificationLock` adds that file (834 MB, from the Hub repository at the pinned commit) to the entity lock.

The capability `classification` is now `experimental` on `gliner2-base-v1/onnx-fp32-cpu`. On 26 proposed cases run by the pinned GLiNER2, input ids and decisions were exact, logits were within 2.74e-5 relative and scores within 8.46e-6 (`docs/evidence/gliner2-classification-2026-11-01/`). It stays `unsupported` on CUDA: the classifier rejects CUDA sessions. Several tasks per call, label descriptions, temperature and batching are `unsupported`. There is no task-quality set yet, and parity is not quality: at least 2 of the 19 single-label answers in those cases are wrong for GLiNER2 itself. Entity extraction is unchanged: the protected entity parity passes, with exact inputs.

## Starlings.Models.EmbeddingGemma2: opt-in vision batch limits from free memory (experimental, #172)

New `EmbeddingGemma2MultimodalOptions.AutoBatchLimits` (`EmbeddingGemma2AutoBatchLimits`, default `null`: off). When set, `EmbeddingGemma2MultimodalEmbedder` reads the free memory of the vision graph's device once after load (Linux host `MemAvailable`, capped by the least room under a cgroup v2 `memory.max` of the process's cgroup or its ancestors, on CPU; `cuMemGetInfo` of the CUDA driver, capped at `gpu_mem_limit` when set, on CUDA) and raises `MaxVisionBatchSize`, `MaxVideoFramesPerVisionCall` and `MaxVisionBatchPatches` to what fits in `(free - ReservedBytes) * UsableFraction` (defaults 1 GiB and 0.5), with an estimate of 3 GiB per full-budget image derived from the CUDA observations behind the defaults. Configured values are floors; `MaxImagesPerCall` (8) and `MaxFramesPerCall` (16) cap the raise; the text-graph limits are not changed. With the option set, vision-graph calls run one at a time; batched CUDA outputs match single calls within about 3.4e-5, not bit for bit. `EmbeddingGemma2MultimodalEmbedder.AutoBatchAvailableBytes` reports the bytes read (`null` when the probe is unavailable, and then the configured limits apply). Capability `image.auto_batch_limits`: Experimental (the estimate is not measured per device; no qualification run). The defaults are unchanged, so no Stable contract moves. The CUDA probe was checked on an RTX 4060 Ti (opt-in CUDA test), which supports Experimental only.

## Hub checkpoint locks for QwenChat and Kev (#246)

The definition packages now pin the Hub checkpoints themselves, as `Starlings.Models.Qwen35` does for Qwen3.5 (`Qwen35Checkpoint.Lock`). Additive except for `KevModelProfile`'s two new `required` members (below, and in [`BREAKING.md`](BREAKING.md)); no bundle lock, profile, capability status, gate or `protected/` file changed, and nothing downloads unless a lock is passed to `ModelAssetStore.DownloadAsync`.

- **`Starlings.Models.QwenChat`**: `QwenChatCheckpoint.Lock` and `LockFileName` for `Qwen/Qwen3-0.6B` at `c1899de2` and `Qwen/Qwen2.5-0.5B-Instruct` at `7ae55760`: `config.json`, `generation_config.json`, `merges.txt`, `model.safetensors`, `tokenizer.json`, `tokenizer_config.json` and `vocab.json` (1,519,182,365 and 999,586,347 bytes). Packed as `locks/qwen3-0.6b.checkpoint.lock.json` and `locks/qwen2.5-0.5b-instruct.checkpoint.lock.json`.
- **`Starlings.Models.Kev`**: `KevModelProfile.CheckpointLock` (Kev's own repository: `adapter_config.json`, `adapter_model.safetensors`, `head.pt`, `provenance.json`, `tokenizer.json`, `tokenizer_config.json`) and `BaseCheckpointLock` (the frozen base `Qwen/Qwen3.5-0.8B-Base` or `Qwen/Qwen3.5-4B-Base`: configuration, safetensors weights and index, tokenizer files and the two preprocessor configurations), with `CheckpointLockFileName` and `BaseCheckpointLockFileName`. Packed as `locks/kev-0.8b.checkpoint.lock.json`, `locks/kev-4b.checkpoint.lock.json`, `locks/qwen3.5-0.8b-base.checkpoint.lock.json` and `locks/qwen3.5-4b-base.checkpoint.lock.json`. `KevModelProfile`'s two new members are `required`, so code that builds its own `KevModelProfile` with an object initializer must set them (`with` copies are unaffected).
- **Source of the digests.** Each lock is the pipeline candidate contract's `origin.files` (`model-pipeline/candidates/{qwen3,qwen25,kev-0.8b,kev-4b}/profile.json`; for the base, `origin.base.files`) without the model card and license. On 2026-11-01 every size and every LFS SHA-256 agreed with the Hub's file listing at the pinned revision, and the SHA-256 of every non-LFS file was recomputed from the downloaded bytes; no weights were downloaded. Tests in both packages check that the C# lock equals the packed JSON (`ModelAssetLock.Load`, `schema_version` 2) and the candidate contract, and that it agrees with the checkpoint's tokenizer, adapter and head digests.
- **Dependency.** Both definition packages now reference `Starlings.Acquisition` (BCL only, no ONNX Runtime) for `ModelAssetLock`, as `Starlings.Models.Qwen35` does; the dependency-boundary tests now require it instead of forbidding it.

## New packages: Starlings.Models.Qwen3Embedding and .Extensions.AI (Experimental, source only; #144, #108, #100)

`Qwen/Qwen3-Embedding-0.6B` text embeddings (`Qwen3TextEmbedder`, an `ITextEmbedder`: last-token pooling, L2, 1024 floats, named prompts `none`, `document`, `query` and `FormatQuery` for custom instructions) and `Qwen/Qwen3-Reranker-0.6B` reranking (`Qwen3Reranker`, an `IReranker`: raw log-odds `logit[yes] - logit[no]`, custom instructions, `Rank`, `Sigmoid`) on ONNX Runtime CPU, fp32, with tokenization from `Starlings.Tokenizers` (profiles `qwen3-bpe-embedding`, `qwen3-bpe-chat`). `Starlings.Models.Qwen3Embedding.Extensions.AI` adds `Qwen3EmbeddingGenerator`, an `IEmbeddingGenerator<string, Embedding<float>>`. Built-in profiles `qwen3-embedding-0.6b` and `qwen3-reranker-0.6b` pin the upstream commits and the size and SHA-256 of every file of the directory that the recipe in `model-pipeline/reference/qwen3-embedding/` builds; a directory is verified before loading. The graphs are hosted publicly at `Starlinghq/qwen3-embedding-0.6b-onnx` (`0585005027acc7232133808914cd8bc2a4bd1ea8`) and `Starlinghq/qwen3-reranker-0.6b-onnx` (`0f951df2baec8e9ac7f884f349d2820a34aa85e5`) with their NOTICE and license; the profiles' locks download every file from there (`ModelAssetLock.Hosting`), and the new `Qwen3EmbeddingModelAssets.DownloadAsync` and `OpenLocal` fetch and open them explicitly (capability `Download` is now experimental). Every capability is experimental or unsupported (`Qwen3EmbeddingCapabilities`; CUDA and Matryoshka dimensions are unsupported because the package has no CUDA session and rejects other dimensions). The new onboarding route `qwen3-embedding-onnx-cpu-v1` (.NET stage `Starlings.Qwen3Embedding.Fidelity.Tool`) ran on CPU (`docs/evidence/qwen3-embedding-onboarding-2026-11-02/`): the embedding passed (558 checks) and has the registry profile `qwen3-embedding-0.6b/onnx-fp32-cpu` (Experimental); the reranker failed the predeclared hidden-state bound on two long inputs (scores within 2.4e-5) and has no registry profile yet. The packages are not in the release drill. Tests that need a graph read `STARLING_QWEN3_EMBEDDING_RELEASE` and `STARLING_QWEN3_RERANKER_RELEASE` and skip without them. `tools/fetch-tokenizer-assets.sh` also fetches the pinned `Qwen/Qwen3-Embedding-0.6B` tokenizer.

## Starlings.Models.Qwen35.OnnxGenAI: int4 on CPU (Experimental; #163)

New `Qwen35Variant.Int4` and registry profile `qwen3.5-0.8b/ortgenai-int4-cpu` (Experimental). The graph is the ONNX Runtime GenAI 0.17.1 builder's int4 CPU recipe (`-p int4 -e cpu`: round-to-nearest, block 32, accuracy level 4) on the float32-overlay snapshot, built with `model-pipeline/reference/generation/build_ortgenai_bundle.py --variant int4`. Its weights file is byte-identical to the M0 int4 build. It is hosted since hosting revision r2 (next section): `Qwen35ModelAssets.DownloadAsync(Qwen35Variant.Int4)` downloads and verifies it (new `Qwen35ModelAssets.IsHosted`, true for every variant), and a local build with the same digests opens with `OpenDirectory`. `Qwen35ChatModel.Load` rejects it on CUDA. The claim is parity with the upstream Python binding on the same int4 graph (new runner `run_genai_reference.py`, proposed fixture `model-pipeline/proposed/qwen3.5-0.8b/ortgenai-int4-cpu`), not fidelity to the checkpoint: int4 matches 1 of 22 fp32 reference sequences. New capability keys: `chat.greedy.int4.cpu`, `quantized.int4.cpu` and `asset_acquisition.download.int4` (experimental), `int4.cuda` (unsupported). `quantized` stays unsupported on the Stable profiles. No tolerance or task-quality floor exists yet; the maintainer sets them in a protected change. Evidence: `docs/evidence/qwen35-int4-cpu-2026-11-01/README.md`.

## Starlings.Models.Qwen35.OnnxGenAI: hosting revision r2, int4 download and guided decoding on the hosted files (#139, #163)

`Qwen35ModelAssets.HostingRevision` moves from r1 (`95a690c1774f144957cb7b76986a9126e8b1bb5f`) to r2, `22477cdb8a2dc71f4c98d2e6af0a046ec0d74f45` of `Starlinghq/qwen3.5-0.8b-ortgenai`. r2 keeps every r1 file unchanged and adds, in one Hub commit:

- `ortgenai-int4/` (`genai_config.json`, `model.onnx`, `model.onnx.data`; 541,890,291 bytes): the int4 CPU graph of the Experimental profile `qwen3.5-0.8b/ortgenai-int4-cpu`, rebuilt with `build_ortgenai_bundle.py --variant int4` to the digests the 2026-11-01 evidence recorded. `DownloadAsync(Qwen35Variant.Int4)` no longer throws; `asset_acquisition.download.int4` is experimental and the profile's `rights.redistribution` is `download`. The profile stays Experimental.
- `tokenizer.json` (a copy of `transformers-5.18.0/tokenizer.json`, 19,989,339 bytes) and `tokenizer_config.json` (the checkpoint's file at the pinned revision, unchanged, 16,709 bytes; the digest `Qwen35Checkpoint.Lock` pins) in each of `ortgenai-fp32x/`, `ortgenai-fp16x/` and `ortgenai-int4/`: the files ONNX Runtime GenAI's guided decoding opens from the model directory (#139 part 2). Each variant's lock now lists both (new `Qwen35ModelAssets.VariantTokenizerFile`, `VariantTokenizerConfigFile`, `TokenizerConfigSha256`), and the bundle script writes and checks them.

Guided decoding from the downloaded r2 files passed on fp32x on CPU (`GuidanceCpuModelTests`, `GuidedRealModelTests`) and on fp32x and fp16x on CUDA (new `CudaGuidanceTests`, on an RTX 4060 Ti, not the qualification RTX 3090), so `structured_output` (package table and the fp32x-cpu, fp32x-cuda and fp16x-cuda profiles), the new `structured_output.cuda`, `extensions_ai.tool_mode.required` and `extensions_ai.structured_output` move from unsupported to **experimental**. On the int4 profile `structured_output` is untested (no guided run on int4). The test helper that assembled a temporary guided directory (`STARLING_QWEN35_TOKENIZER_CONFIG`) is removed. Evidence: `docs/evidence/qwen35-hosting-r2-2026-11-02/README.md`.

**Upgrading:** a cache acquired before this change lacks the two new files of each variant directory, so `Qwen35ModelAssets.OpenLocal` and `OpenDirectory` throw `ModelAssetMissingException` until `Qwen35ModelAssets.DownloadAsync` runs again (it fetches only the missing files: about 20 MB for fp32x or fp16x; int4 was never downloadable, so its first download is about 0.58 GB). This applies to requests that never use guidance too: the lock is one set of files. A directory built locally with an earlier bundle script needs the same two files; the current script writes them.

## Starlings.Models.Kev: KevState on CUDA (#140)

`state_reuse_across_calls.cuda` moves from untested to **experimental**. The KevState tests now also run in the local CUDA test project (`CudaParityTests.StateReuseEqualsDecideBitForBit`, `StateIsSharedByConcurrentCallsAndRefusedAfterDispose`). On `kev-0.8b/onnx-fp32-cuda`, decisions from a `KevState` equal `Decide(request)` on the same CUDA session bit for bit: the nine request goldens, twice in a row and question by question, and from four concurrent callers. This passed in 3 of 3 processes on an RTX 4060 Ti, not the RTX 3090. Kev-4B on CUDA was not run, since it needs about 17 GB of device memory. No code change. Evidence: `docs/evidence/kev-state-cuda-2026-11-01/`. The GPU-resident `-e cuda` graph (#140 ask 1) and cross-request prefix reuse are still open.
